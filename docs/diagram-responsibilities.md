# 図の責務と描画の受け渡し

## 決定と目的

Diagram Desk は、エージェントが編集したソースを人間が図で確認する場とする。
図の内容・図の表現・閲覧の場の3つの責務を分ける。ソースを正本とし、生成した SVG は表示結果として扱う。
Diagram Desk が受け付ける入力は SVG に限定しない。`.mmd` などの形式を順次追加できる構成とする。
本書はこの責務分担を採用する設計方針である。「現行」と明記した契約以外の追加機能は未実装。
この変更は文書のみで、描画モジュールの移動や既存編集機能の変更は含まない。

優先する確認の流れ:

1. エージェントが対象リポジトリの正本を編集する。
2. 形式側がソースの意味・参照の整合性を検証し、図として描画する。
3. Diagram Desk が変更を取得し、表示を更新する。
4. 人間が要素・関係・詳細を確認し、対象ファイルや要素 ID を使って指示を返す。

人間がソースを読まなくても内容をたどれ、必要なときはソースに戻れることを目指す。
形式固有の意味を変える画面編集は、最初の共通契約には含めない。

## 責務の所有者

| 責務 | 所有するもの | 所有しないもの |
| --- | --- | --- |
| 図の内容 | 正本の形式、要素 ID、意味、参照、整合性検証、形式の互換性 | 表示位置や色、リポジトリ一覧 |
| 図の表現 | 配置、形、色、SVG、図固有の選択・強調・詳細表示 | ファイル探索、HTTP、監視、正本への保存 |
| 閲覧の場（Diagram Desk） | 対応形式とアダプターの登録、リポジトリ登録、図の探索、URL、取得、変更通知、プレビュー、パン・ズーム、エラー表示 | Onion の層や VPD の顧客価値の意味、各形式の配置規則 |

図の内容と図の表現は別責務だが、同じ形式の仕様に追従する一つのモジュール群として管理できる。
たとえば Onion のスキーマ・検証・配置・描画はまとめて変更できるようにする。
Diagram Desk はその公開入口を登録して呼び出す。独立した責務が、そのまま別リポジトリを意味するわけではない。

Diagram Desk に残す検証はパス、アクセス範囲、転送する値の型など。
「関係の参照先が存在するか」「この要素をこの層に置けるか」は形式側が決める。
保存時の競合検知は閲覧の場が持つ既存機能として維持する。

## 現行の構成と契約

main の対応形式は Mermaid (`.mmd`) と Onion (`.onion.json`)。
VPD は未接続で、`vpd-tools` が独自の Web キャンバスと保存処理を持つ。

| 入口 | 現行の役割 |
| --- | --- |
| [shared/diagram-formats.mjs](../shared/diagram-formats.mjs) | 形式 ID・拡張子・ラベル・種類、共通のパス検証 |
| [public/renderers/index.mjs](../public/renderers/index.mjs) | パスから描画アダプターを選ぶ |
| [public/renderers/onion-model.mjs](../public/renderers/onion-model.mjs) | Onion のモデル検証と配置 |
| [public/renderers/onion.mjs](../public/renderers/onion.mjs) | Onion の SVG・選択・詳細表示 |
| [public/viewer.mjs](../public/viewer.mjs) | ソース取得・更新反映・描画呼び出し・編集と保存 |
| [public/diagram-previews.mjs](../public/diagram-previews.mjs) | 形式を問わずサムネイルを描画・キャッシュ |
| [public/canvas-viewport.mjs](../public/canvas-viewport.mjs) | SVG のパン・ズーム・全体表示 |

既存の描画アダプター契約:

```js
// 形式ごとのアダプター。source は単一ファイルの全文文字列。
{
  id,
  createState(),
  highlight(source),
  async render(source, { id, state, mode }),
  handleEvent({ type, event, source, state, canvas, graph }) // 任意
}
```

- `createState()` は表示ごとに独立した状態を作る。プレビューと詳細で共有しない。
- `render()` の `id` は SVG 内部 ID の衝突を避けるための描画 ID。ソースの要素 ID とは別物。
- `mode` は `preview` または `detail`。結果は `{ svg, detail? }`。`detail` は詳細表示用 HTML。
- `highlight()` はエスケープ済みの構文色分け HTML を返す。既存エディター用の契約。
- `handleEvent()` は現在 click/dblclick を受け、表示状態を変えたときに truthy を返す。ホストが再描画する。
- 描画に失敗すると例外で通知し、Viewer がメッセージを表示する。構造化した診断はまだ返さない。

現在の取得・保存は単一ファイル単位。詳細表示中のファイル変更をサーバーが定期確認し、SSE で通知する。
未編集なら新ソースを受け入れて描画し、未保存の編集があれば競合を通知する。
一覧全体のライブ更新や複数ファイルの整合したスナップショットはこの契約に含まれない。

## 次に整える境界

### 外部入力と内部の表示結果を区別する

Diagram Desk のファイル入力と、描画アダプターからキャンバスへの出力は別の境界とする。
「キャンバスが SVG を表示する」ことは「利用者が SVG に変換してから渡す」ことを意味しない。
Diagram Desk は登録された入力形式を取得し、対応するアダプターを呼び出して表示する責務を持つ。

| 外部から渡す形式 | 図の表現を決める側 | Diagram Desk が担う接続 | 対応状況 |
| --- | --- | --- | --- |
| `.mmd` | Mermaid エンジン | Mermaid アダプターがソースをエンジンへ渡し、SVG と形式固有の閲覧操作を接続する | 現行 |
| `.onion.json` | Onion の検証・配置・描画モジュール | Onion アダプターを呼び出し、描画結果と詳細を表示する | 現行 |
| `.svg` | SVG を作成したツールまたは作成者 | SVG 用アダプターで読み込み、表示可能な内容に処理してキャンバスへ渡す | 今後追加できる候補 |
| VPD の正本群 | VPD の読み込み・描画モジュール | 複数ファイルの取得・更新と VPD アダプターを接続する | 未接続 |

Mermaid の構文・自動配置・SVG 生成は Mermaid エンジンが所有し、
Diagram Desk はそのエンジンを利用するアダプターを提供する。
描画エンジンを呼び出すことは、図固有の配置アルゴリズムを Diagram Desk の共通部へ実装することとは区別する。
図の表現という責務は、Desk に同梱したモジュールでも外部ライブラリでも担える。

対応形式は、拡張子・形式 ID・メタデータの定義と、描画アダプターを一組として順次追加する。
拡張子を登録するだけで表示可能とは扱わず、探索・取得・プレビュー・詳細・更新反映まで確認して対応とする。
共通のファイル処理やキャンバスへ形式固有の分岐を広げず、形式の選択は登録箇所に集約する。

SVG を直接受け付ける場合も、取得した全文をそのまま DOM に挿入する契約にはしない。
スクリプト・イベント属性・外部参照などの扱いと、内部 ID の衝突回避を SVG 対応時に定める。
元データの要素 ID や診断を持たない SVG も、基本表示は可能にする方針とし、確認情報は形式の能力に応じて追加する。

### 入力は意味を保ったソース

Onion を共通のノード・エッジ形式へ変換することは要求しない。
形式 ID と元のソースを対応する描画モジュールへ渡し、図の形態はモジュールが決める。
共通化する対象は読み込み・描画・表示操作の手順とする。

単一ファイル形式では現行の `source` を維持する。
VPD のような複数ファイル形式では、正本を一つの巨大な SVG や別の編集用 JSON に置き換えず、
形式側の読み込み処理が正本群から表示用データを組み立てる。
ファイルへのアクセスと変更監視は Diagram Desk の入口を利用し、描画コードには渡されたデータだけを読ませる。

VPD の接続前に、図の入口となる識別子、依存ファイル一覧、依存先が増減した場合の再探索、
一組の読み取り中に更新が入った場合の再取得を設計する。
現行の単一文字列契約で複数ファイルの更新反映まで実現できるとは扱わない。

### 出力は図と確認情報

アダプターからキャンバスへの最初の内部表示契約は、既存の SVG と詳細表示を利用する。
外部入力は `.mmd` などの元形式のまま受け付け、共通のキャンバスへ渡す前にアダプターがこの契約を満たす。
全形式を扱う汎用シーングラフや、実行時に任意コードを読み込むプラグイン機構は導入しない。
形式モジュールは開発時に明示的に登録する。

次の情報は段階的に追加する目標であり、現行アダプターの必須項目ではない:

| 情報 | 目的 | 責務 |
| --- | --- | --- |
| ソース参照（ファイル、安定した要素 ID、必要なら位置） | 人間が指した要素をエージェントが特定する | 形式側が対応を作り、Desk が表示する |
| 診断（重大度、理由、ソース参照） | 不正なソースを双方が直せる | 形式側が生成し、Desk が提示する |
| 表示対象のソース版 | 古い表示と最新ソースを区別する | Desk が取得版と描画結果を対応づける |

行番号だけを識別子にせず、形式に安定した要素 ID があれば優先する。
SVG の描画 ID は再描画のたびに変わり得るため、確認対象の識別には使わない。
共通側は層・付箋などの種類を解釈せず、形式側が返す参照と詳細を扱う。

### 操作と更新

選択、関連要素の強調、詳細表示、枠の開閉は閲覧のための操作として形式側へ委譲する。
パン・ズームと画面遷移は Diagram Desk に残す。
閲覧操作は正本を書き換えない。内容の追加・削除・関係の変更は各形式のツールが担当する。

非同期描画では、古い描画結果が新しいソースの結果を上書きしないようにする。
現行 Viewer の serial による結果の破棄を維持する。
ソース変更後に存在しなくなった選択をどう解除するかは形式側が扱う。

描画失敗時に最後の成功図を残すなら、それが最新ソースの図ではないことを明示する。
現行 Viewer はエラーメッセージを出すが、図に取得版や古い表示の印は付けない。これは改善項目とする。

## Onion と VPD の適用

Onion は既存のモデル・配置・SVG 描画を形式モジュール群としてまとめる。
独自のサーバーやファイル監視を追加せず、単独での描画確認と Diagram Desk からの呼び出しを可能にする。

VPD は `vpd-tools` が正本の Markdown/YAML、検証、内容編集を所有する。
Diagram Desk が同じ形式を再定義せず、形式側の読み込み・描画入口を利用する形を検討する。
既存キャンバスの表示と編集がどこまで分離できるかは、接続前に確認する。
VPD の台紙、付箋、関連線の描画を Diagram Desk 側にもう一つ実装しない。

## 移行の順序と完了条件

各段階は独立した変更として進める。

1. **責務と契約を文書化する（本変更）**
   現行と目標の違い、外部入力形式と内部表示結果の違いが確認でき、README からたどれる。
2. **Onion の境界を実装で明確にする**
   形式モジュールが Desk の取得・保存・監視に依存せず、渡されたソースから描画できる。
   単独描画、Desk のプレビュー・詳細表示、選択・強調、既存の更新反映を検証する。
   CSS や暗黙のブラウザ依存も調べ、必要な表示資産を公開入口に含める。
3. **確認用の参照・診断・表示版を整える**
   要素をソースへ対応づけ、不正な更新とその修正を確認できる。
   正常な更新・不正な更新・修正・連続更新で、表示と正本を取り違えないことを検証する。
4. **VPD を接続する**
   複数ファイルの読み込みと変更検知を定義し、`vpd-tools` の正本・描画を利用する。
   各依存ファイルの更新と読み取り途中の変更を検証する。

物理的なパッケージ分離は、Onion の単独描画で境界を確かめた後に判断する。
当面の実装で先回りして汎用の編集 API や別の正本を作らない。
